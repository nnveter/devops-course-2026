# Git vs SVN

## 1. Почему Git называют «распределённым», а SVN — «централизованным»?
В Git у каждого разработчика полная копия репозитория со всей историей: коммиты, ветки, просмотр истории и diff работают локально, без сети, а удалённый репозиторий (origin) — лишь один из равноправных узлов. В SVN история хранится только на центральном сервере, у разработчика есть лишь рабочая копия одной ревизии; любой коммит, просмотр лога или переключение ветки требуют связи с сервером.

## 2. Как в SVN устроены ветки? Почему это «дорого»?
Ветка в SVN — это копия каталога (`svn copy trunk branches/feature`) в общем дереве репозитория. Копия на сервере дешёвая (ссылка), но ветка видна всем, переключение (`svn switch`) скачивает файлы с сервера, а слияние исторически было болезненным: до версии 1.5 не было отслеживания слияний (merge tracking), и повторный merge приводил к конфликтам. Поэтому в SVN ветки создают редко и надолго. В Git ветка — указатель на коммит размером 41 байт, создаётся и переключается мгновенно и локально.

## 3. В каких случаях SVN может быть предпочтительнее Git?
- Репозитории с большими бинарными файлами (игровые ассеты, CAD-модели, дизайн), где нужна блокировка файлов (`svn lock`) — Git без LFS хранит каждую версию у каждого.
- Когда нужно выдавать доступ к отдельным подкаталогам (path-based authorization) и выгружать только часть дерева (sparse checkout «из коробки»).
- Legacy-проекты и корпоративные процессы, построенные вокруг линейной нумерации ревизий (r1234) и единого центрального сервера.
